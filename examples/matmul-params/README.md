# Example: one benchmark, several parameter combinations; comparisons across parameters

In this demo, we show 

- how to run a parametrized benchmark: time a matrix multiply, `a @ b`,
for square arrays of several sizes, represented as numpy arrays and torch tensors.

- how to arrive at a *comparison verdict*  across "variants": is matrix multiply in
  NumPy faster or slower than PyTorch's?

The first part follows the
[UC-01](https://github.com/benchx-dev/benchx/blob/main/docs/use-cases/UC-01-short-slug.md) shape,
and second part is a
[UC-02](https://github.com/benchx-dev/benchx/blob/main/docs/use-cases/UC-02-variants.md)
benchmark: the same function, run once with each library, with the rounds interleaved. 


## Install the required dependencies


```sh noexec
python -m venv .venv && . .venv/bin/activate
pip install benchx[parquet]
pip install pyperf numpy
pip install torch --index-url https://download.pytorch.org/whl/cpu    # the CPU build
```

This uses pyperf's defaults (20 worker processes x 3 values, 0.1 s calibration) and takes several minutes, mostly importing torch in every worker.

## Run a quick version

By default, `benchx` uses `pyperf`'s defauls: 20 worker processes x 3 values each, and 0.1s calibration.
In this demo, we use a quick-and-dirty version, so that the run time is smaller but the results will be noisy 

```sh
$ export QUICK="--processes 2 --values 2 --min-time 0.01"
$ bx bench bench_matmul.py $QUICK
```

## Choosing cases

We can select specific cases by either giving exact parameter values or a regex. Note that since we are parametrizing
the benchmark with string arguments, we have to use the quoted strings in CLI.

```
$ bx bench bench_matmul.py bench_matmul                  # a function's name: all six
$ bx bench bench_matmul.py "bench_matmul(100, 'torch')"  # one combination
$ bx bench bench_matmul.py --filter "'torch'"            # a regex: the three torch cases
```

A regex is searched in `bench_matmul(10, 'torch')`, the function's name and the argument
values (not their names). `--filter 'bench_matmul$'` is therefore refused, since `$` leaves
no room for the arguments; the refusal says so.


# Comparing numpy and torch

Suppose now we ask: is PyTorch matmul faster than NumPy matmul for the same matrix size?
We can of course, visually inspect the output above, and try to guesstimate the spread of the results
(shown in the `min..max` column).

`benchx` however provides a better way to perform a comparison and run a statistical analysis to come up with
a _comparison verdict_ (faster, slower or indeterminate). The relevant CLI command is `bx compare`.

Next, we supply the following parameters to `bx compare`:

- we compare across *variants*: same function, varying values of its parameter: `--profile variants`;
- we vary the `xp` parameter and compare for each value of the other parameter `n`: `--vary xp`;
- we ask whether the *contender* PyTorch is measurably faster than the *baseline* NumPy: `--baseline "'numpy'"`; Note that
  the double quotes here are not a typo: in Python, we parametrize the benchmark function with strings, thus we need to
  keep the quotes in the CLI invocation.

Taking it all together, we run

```bash
$ RUN=$(bx head -n 1 | awk 'NR==2 {print $4}')
$ bx compare --profile variants --run $RUN --vary xp --baseline "'numpy'"
```

## A proper comparison requires an alternating run

Here we are facing a design constraint of `benchx`: to produce a comparison verdict, it needs to
run the comparison sides multiple times, and interleave the runs. This way, it can estimate the noise
and control for possible drift in the benchmarking environment.

To run the comparison, we need to explicitly to provide the `--rounds N` argument, where each
side of the comparison will be run `N` times. Increasing the number of rounds improves
the quality of the statistical estimates, at the expense of longer run times.
Taking this all together:

```bash
$ export QUICK="--processes 2 --values 2 --min-time 0.01"
$ bx compare . --profile variants  --suite bench_matmul.py --vary xp --rounds 5 $QUICK 
```

### Show all comparison results, as a table

The output above only shows "effects" and does not show actual timings. To show both, we could have
added `--table --all` to the `bx compare` call. Given that we did not add it, we can rerun the
comparison (but not the benchmarks themselves!) in the so-called *run mode*, where it pulls the
data to compare from the store.

First, instead of the benchmark suite, it needs the run key for the precomputed data.
Then, we give it the same `--profile variants --vary xp` arguments to specify what to
compare, and also we tell it which side is the baseline, `--baseline "'numpy'"`
Taking it all together,

```bash
$ RUN=$(bx head -n 1 | awk 'NR==2 {print $4}') 
$ bx compare --run $RUN --profile variants --vary xp --baseline "'numpy'" --tables --all
```

## A manual loop + "run mode" comparisons.

Above we used `bx compare` in the so-called *measure mode*, where it ran the benchmarks under the comparison schedule. An alternative, more
manual, way is to run a loop over `bx bench` calls and then invoke `bx compare` in the *run mode*, as before.

For the first step, we need to handle alternating the sides manually: Each call runs one library,
with `--filter`, as one side of a session; we use `--round` and `--slot` to place it into the comparison sequence;
we also need to specify the same run key for all calls, via the `--run-key` argument.

```
for r in 0 1 2; do
  bx bench bench_matmul.py --filter "'numpy'" --run-key mm --round $r --slot $((2*r))   $QUICK
  bx bench bench_matmul.py --filter "'torch'" --run-key mm --round $r --slot $((2*r+1)) $QUICK
done
```

The output (not shown) will be somewhat noisy because every `bx bench` call prints out its measurements.
Once the data is computed, we run the comparison in the run mode by specifying the `--run RUN_KEY` 

```
$ bx compare --run mm --profile variants --vary xp --baseline "'numpy'"
```

The resulting output will be the same as the measure mode comparison (since we used quick-and-dirty settings,
results are not reliable and may thus differ though). 


## Final remarks

In the second part of this example, we demonstrated two ways of running a comparison: the *measurement* mode,
where `bx compare` runs benchmarks itself, and the *run* mode, where we run benchmarks in a manual loop.
Why would one use the second variant over the measurement mode, as it looks to be more work for no gain?

For the *variants* comparison it is indeed unnecessary. However, `benchx` supports several other *comparison profiles*:
`revisions` (where you run comparisons across the history of a project) and `environments` (where you hand
`bx compare` two prepared virtual environments). These kinds of tasks involve building the project or activating
environments---and `benchx` does not do either. This is where the run mode comparisons come in handy. See the
[`pandas-asv` worked example](https://github.com/benchx-dev/benchx_examples/tree/main/examples/pandas-asv) for an
end-to-end demo.
